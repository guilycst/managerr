## Contract and work

- Linked specification sections and relevant invariants: `docs/specs/spec-001-media-reconciliation/data-and-recovery.md` durable action journal and recovery; `docs/specs/spec-001-media-reconciliation/http-api.md` action lifecycle, cancellation and deadline behavior; `docs/architecture/workflow-patterns.md` ordered process manager boundary; `docs/plans/implementation.md` W-02; A-14, A-32 through A-36, A-59 and A-60 in `docs/verification/acceptance.md`.
- Intended result and capability limits: `Executor` is one typed process-manager path for standalone action triggers and later workflow steps. `Journal` is the durable boundary; `SQLJournal` adapts D-01 sqlc rows without exposing generated storage types to handlers. `Claim` and terminal/retry transitions use action version CAS and leases. Reservations serialize overlapping local resources inside a process while the database CAS fences competing workers. The executor observes desired state first, persists ordered observe/dispatch/reconcile attempts and pending per-target effects, and calls a handler only after the dispatch intent transaction commits. A successful dispatch must pass a fresh read-only observe before applied success is recorded. Lost or recovered dispatches enter read-only reconciliation; mutation retry is allowed only after reconciliation proves no effect. Retry times and deadlines are persisted in the action row. Cancellation is a durable marker and deadline/cancellation checks stop the dispatch boundary; a late accepted effect remains in the effect journal under the terminal cancellation/deadline result. Startup recovery turns running actions and attempts into reconciliation without blind mutation retry. There is no generic DAG and no duplicate outbox.
